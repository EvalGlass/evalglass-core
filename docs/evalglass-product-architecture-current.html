EvalGlass product architecture map

A stitched architecture of the product EvalGlass now presents in its documentation and site: how it is structured, how it functions, what the components own, where authority lives, and how the scorecard loop turns AI behavior into bounded quality-control evidence.

Primary source Documentation and reference contracts under public/docs, especially the Trust Model, Evaluation Core, Runtime Harness, Integrations, Vendoring, CLI, Vocabulary, Scorecard JSON, and RunRecord pages.
Secondary source Public site positioning under public/: Home, How it works, Use cases, Scorecards, Extensions, Trust, Local-first, Roadmap, and Get the plugin.
Scope note This is a product architecture as portrayed by the current site/docs. The site and docs intentionally lead parts of the code; status badges show what is now, next, planned, or experimental.

Ground-truth floor: EvalGlass is v0.1.0 pre-alpha, untagged, Apache-2.0, local-first, and not on PyPI. It has no hosted platform, no required provider keys, no telemetry, an empty authority.json by default, and no gate, approve, or certify verb.

Canonical product definition

The product is an AI quality-control loop operated through a coding agent.

EvalGlass is not primarily framed as a generic evaluation framework. It is a practical, repo-native way for AI product teams to ask a coding agent to evaluate an agentic app, turn real behavior into project-specific checks, run those checks locally, and get a scorecard that says what changed and what cannot yet be claimed.

What users do

Ask the coding agent.

The entry point is a product question: model switch, prompt change, drift, new workflow, traces to interpret, a CI gate, or a stakeholder scorecard.

What EvalGlass does

Builds and runs checks.

The agent helps shape project-specific metrics, examples, rubrics, judge evidence, baselines, and scenarios. The vendored runtime evaluates supplied evidence locally.

What users get

A bounded scorecard.

The scorecard shows values, status counts, deltas, diagnostics, authority, and one verdict. It reports what was measured; it never certifies the AI application.

The practical trust line is: runs locally, keeps project truth in the repo, and produces no false green. Trust is not a separate compliance promise; it is the everyday boundary that keeps scorecards useful without overclaiming.

Architecture in one view

From product question to bounded verdict.

The architecture is a chain of responsibility. The coding agent can discover, scaffold, run, and explain. The host repo owns the truth. The Runtime Harness owns effects. The Evaluation Core owns meaning. The Scorecard and RunRecord are the outputs every consumer renders, never recomputes.

1. Product question

"Evaluate this app after the model switch." The user starts from a change or uncertainty in the AI application.

2. Coding-agent surface

The /evalglass umbrella routes setup, connect, run, view, explain, compare, baseline, ci, and authoring verbs.

3. Host repo

EvalGlass vendors managed runtime code into evals/_evalglass/. Everything that grants authority remains host-owned.

4. Runtime Harness

The effectful layer reads config and evidence, runs ports/adapters, converges inputs, persists outputs, and maps verdict to exit code.

5. Evaluation Core

The effect-free core computes Scores, aggregation, provenance, authority, comparability, and the single VerdictPayload.

Optional lanes attach to existing ports without changing the required path: exported trace import is the shipped behavior-input path; live connectors are planned; local scorecard export is experimental; hosted dashboard and prompt-optimizer handoff are next; synthetic generation is planned but governance already forces generated evidence to proposed.

System boundary

Four layers, one responsibility line.

Most EvalGlass trust properties come from this boundary: meaning never performs effects, effects never invent meaning, the installer never grants authority, and domain judgement never moves into the managed framework.

Host-owned truth
Owns Datasets, references, exported traces, rubrics, calibration, approved thresholds, baselines, host evaluators, data policy decisions, and every domain judgement.
Must not own Managed framework internals. The host should not need to patch core meaning to make its domain truth visible.
EvalGlass Skill / plugin
Owns Discovery, planning, vendoring, manifest/lock, starter scaffolds, CI snippets, and guidance through /evalglass verbs.
Must not own Runtime execution, score meaning, metric authority, automatic gating, certification, or silent edits to host truth.
Runtime Harness
Owns CLI, config loading, ports/adapters, input convergence, replay, judge collection, evidence policy, persistence, reports, sinks, and exit mapping.
Must not own New score meanings, ad-hoc verdicts, hidden authority, or report prose that widens what the Scorecard says.
Evaluation Core
Owns Contracts, score semantics, MetricSpec validation, aggregation, provenance, authority resolution, baseline comparability, Scorecard, RunRecord, and the Verdict Engine.
Must not own Filesystem I/O, network, subprocesses, clocks, randomness, model calls, provider SDKs, or domain knowledge.

The key architecture invariant: the Harness calls the Core, but the Core never calls back out. This is what lets one and only one path decide a verdict.

Product workflow

The six-step check loop.

The public site presents EvalGlass as an everyday habit for reviewing AI behavior. The docs then pin every step to a bounded runtime behavior.

Ask

Use natural language or explicit verbs to ask the coding agent what changed, drifted, improved, regressed, or needs review.

Observe

Read repo context, prompts, model calls, examples, release changes, and exported traces. Live provider pulls are planned, not shipped.

Shape

Author project-specific checks: metrics, examples, rubrics, judges, baselines, annotations, and scenarios. Drafts land proposed.

Run

Run the vendored runtime locally. No platform, no provider keys, no telemetry, and no plugin dependency at host evaluation time.

Read

Read Scorecard and RunRecord fields: values, status, validity, diagnostics, authority, baseline state, and verdict.

Improve

Fix prompts, switch models, add examples, review labels, tune metrics, compare against a baseline, or wire CI on a host-approved gate.

Physical structure

Managed runtime vs host-owned truth.

The repo layout is the physical version of host ownership. Re-vendoring may replace the managed column; it must not overwrite the records that decide what a gate means.

      core/
      harness/
      adapters/
      vendor-manifest.json
      evalglass.lock
    evalglass.yaml           # host-owned config

    traces/*.jsonl           # host-owned exported behavior

    rubrics/*.md             # host-owned judge rubrics
    calibration/*.json       # host-owned calibration

Managed

evals/_evalglass/

Core, Harness, adapters, manifest, and lock. Replaced only by deliberate revendor. It grants no authority by itself.

Host-owned

Everything else under evals/

Examples, traces, metrics, rubrics, calibration, baselines, thresholds, approvals, and reports. These records define what can gate.

Evaluation pipeline

Many evidence shapes converge to one typed run.

EvalGlass accepts different evidence routes, but evaluators do not see vendor objects or adapters. The Runtime Harness normalizes everything at the boundary, then the effect-free Core receives typed data only.

Inputs

Host-supplied evidence

DatasetsJSONL examples with optional references and host-owned status.
Exported tracesLocal JSONL, OpenTelemetry export, or OpenInference export. No SDK, no network.
Replay/task outputSubprocess replay with typed failures, not quality scores.
Judge evidenceEvidence collected under data policy; missing/failed judges are not low scores.
Harness edge

Input convergence

TraceEnvelopeVendor-neutral behavior plus metadata, data policy, and provenance.
EvalUnitThe slice evaluated: call, step, trajectory, or session.
ExampleThe evaluator-ready item: input, output, optional reference, context, metadata, provenance.
EvidenceBundleReferences, source material, judge evidence, verifier evidence, runtime errors, and trace fragments.
Core output

Meaning and verdict

ScoresStatus + validity + value only when scored and valid.
AggregationOnly scored + valid values reduce; excluded states remain counted.
AuthorityHost-owned inputs resolve to informational, blocked, or can_gate.
VerdictOne VerdictPayload becomes Scorecard, RunRecord, report, CI exit, and sinks.

Malformed or incomplete input is never quietly dropped. It becomes a diagnostic, a non-evaluable score, an error score, or a blocked active gate, depending on where it occurs.

Runtime trust property

Incomplete cannot pass.

A malformed record becomes visible evidence, not a smaller silent sample. An active gate blocks when required measurement is incomplete.

Runtime trust property

Worst-source authority wins.

Across sources, the weakest dataset status and least-permissive data policy carry forward, so a strong source cannot hide a weak one.

Runtime trust property

Egress before effects.

Data policy is checked before subprocess or judge effects. The allowed egress set is permitted or redacted; anything else fails closed.

Domain model

The core concepts that hold the product together.

The docs define a vocabulary that should remain canonical across site, documentation, code, reports, and future implementation work.

Concept Role in the architecture Claim or authority effect
MetricSpec Declares metric meaning: name, lens, score type, range, direction, evaluator ref, prerequisites, aggregation, threshold, authority, and data policy. Prevents evaluators from quietly emitting scores the metric never declared.
Score One metric result with value, status, validity, diagnostics, evidence refs, evaluator version, and optional subject identity. A value exists only for scored + valid; missing or invalid measurement is never written as 0.0.
Diagnostic Structured reason for a non-perfect state: code, severity, message, location, details, cause, evidence refs. Keeps uncertainty visible and machine-readable instead of burying it in prose.
Authority Typed answer to whether a metric may gate, resolved from host-owned records. Separates a good measured value from permission to enforce CI.
Provenance Run fingerprints across framework, metric spec, evaluator, dataset, example, evidence, config, policy, authority, and baseline. Defines when a comparison or regression claim is supported.
Baseline comparability State machine: comparable, not_comparable, missing_baseline, comparison_not_requested. Blocks regression claims across mismatched runs.
DataPolicy Per-source egress state: permitted, redacted, forbidden, missing, or unknown. Only permitted or redacted evidence may cross an effect boundary; other values block an authorized gate.
Scorecard Primary summary artifact: verdict, metrics, authority, baseline state, diagnostics. Reports, CI annotations, and sinks render this; they do not recompute it.
RunRecord Complete reproducible record: run_id, embedded scorecard, every Score, provenance, and comparability result. Provides auditability and per-call grouping through explicit example_id/unit_id.
ExtensionLane / LaneResult Metadata-only optional capability declaration, plus ran/skipped/blocked result with diagnostics. A lane can carry evidence or output; it cannot carry a score, authority, or verdict.

Trust model

Term separation

Status is overloaded unless scoped.

Always qualify which status is meant: public claim status, metric status, dataset status, score status, judge evidence status, baseline state, lane outcome, or verdict.

Claim separation

Scorecard is not RunRecord.

The Scorecard is the bounded readable claim. The RunRecord is the complete reproducible record. Reports and sinks render them; they do not decide again.

Capability separation

Extension is not evaluator.

An evaluator produces Scores from typed Examples and evidence. A lane can supply evidence, diagnostics, or output through a port, but remains outside the scoring and authority path.

Architecture laws

The laws that fall out of the ontology.

Cross-checking against the deeper architecture file makes the core laws clearer. These are the assertions that future implementation alignment should be able to prove or falsify.

Verdict decides once.

A run outcome is formed only by the Evaluation Core's Verdict Engine, from measurement and authority.

Authority starts with the host.

Capability never grants authority. Only host-owned records can make a metric enforceable.

Scorecard bounds the claim.

A scorecard licenses only what this run measured under supplied evidence, policy, baselines, and authority.

Missing is not zero.

A missing or untrusted measurement is null with status and diagnostics, never a silent 0.0.

Deltas need comparability.

A regression claim exists only when two runs are typed comparable by provenance.

CI reads the payload.

CI should act on typed verdict or exit mapping: pass/informational exit 0, fail/blocked exit 1, infrastructure exit 2.

Lanes carry no authority.

Optional lanes return evidence, diagnostics, or output only, and required paths stay valid when lanes are removed.

Fresh install gates nothing.

Starter assets are proposed, thresholds unapproved, judges uncalibrated, and authority records empty.

Claim boundary and authority

A green result is a bounded statement, not proof of correctness.

EvalGlass asks a precise question: given the supplied evidence, authority records, metrics, thresholds, calibration, baselines, and data policy, what Scorecard and verdict can it honestly emit?

The bounded product claim

EvalGlass can honestly emit this Scorecard and verdict from the supplied evidence and host-owned authority records. Anything beyond that, such as "the model is correct" or "the release is safe", remains a human and host inference.

Measurement filter Only scored + valid values enter aggregation. Blocked, non_evaluable, skipped, error, invalid, and not_measured states are excluded but counted.
Authority filter Dataset status, threshold approval, metric status, judge calibration, data policy, and baseline state decide whether a metric can gate.
Comparability filter A delta is a regression claim only when baseline fingerprints match on the gating dimensions.
Verdict filter The Verdict Engine is the single path. Consumers render the VerdictPayload; they never decide again.
informational

Evidence, no active gate.

Common first-run state: proposed data, unapproved threshold, uncalibrated judge, or metric not set to gating. Useful, but not enforcement.

blocked

Gate active, claim unsound.

The metric is configured to gate, but evidence, policy, comparability, calibration, or measurement completeness cannot support an honest claim.

can_gate

Threshold enforced.

The metric cleared host-owned authorization and evidence-soundness checks, so its value is compared to the approved threshold.

Run outcomes

One verdict, one CI signal.

The Scorecard resolves to exactly one verdict. CI should branch on the typed verdict or exit code, not report prose.

Verdict Meaning Exit code Important reading rule
informational Measured evidence, but no active gate ran. 0 Exit 0 does not mean quality was enforced.
pass Active gates met their approved thresholds. 0 Pass is bounded to the checks, evidence, and authority records of this run.
fail An active gate was validly measured and missed its approved threshold. 1 Fail means "we know and it is short."
blocked An active gate could not be claimed honestly. 1 Blocked means "we cannot say"; it still fails CI when a gate is active.
infrastructure error The run itself could not complete. 2 Not a quality verdict; there is no trustworthy Scorecard verdict to enforce.

The VerdictPayload is not just a label. The reference docs state that it re-derives itself and fails closed on tampering, so a consumer cannot hand-set a friendlier verdict without contradicting the typed gate lists.

Ports and adapters

Effects enter through six narrow seams.

Integrating a backend means implementing a port, not changing the core. Adapter outputs carry evidence or diagnostics; they never emit scores, authority, or verdicts.

Port Purpose Required adapter shape Boundary rule
DatasetStore Read examples, references, dataset status, and version. Local JSONL examples and references. Malformed records become diagnostics, not silent exclusions.
TraceSource Yield recorded host behavior as TraceEnvelopes. Local JSONL and open-convention trace export mapping. Vendor objects are dropped at the edge.
TaskRunner Replay host outputs when needed. Subprocess JSON in/out. Failures become typed diagnostics with missing output.
JudgeModel Collect judge evidence when a metric declares it. Deterministic fake judge in the required path; live judge is optional. Judge evidence is not authority; calibration is host-owned.
ResultStore Persist RunRecords, Scorecards, reports, and baselines. Filesystem JSON/JSONL. Persists results; never recomputes a verdict or promotes a baseline.
ScoreSink Render immutable results outward. Markdown, terminal, JSON, CI annotations, optional export sink. Can render or publish; cannot mutate typed results.

Command surface

The coding-agent interface is useful but deliberately non-authoritative.

The absence of gate, approve, and certify verbs is part of the architecture. The plugin can scaffold, run, and explain; only host-owned records can grant authority.

Surface What it does Authority rule

setup Discover candidate call sites, vendor runtime, scaffold proposed dataset/metrics/CI, or revendor managed code. Discovery is candidate inventory, not proof of completeness; scaffolds are non-authoritative.

Artifacts

Scorecard is the readable artifact; RunRecord is the full record.

Every external presentation should flow from these typed artifacts. Reports, terminal summaries, CI annotations, dashboard sinks, and optimizer handoffs should not decide anything.

Primary summary

scorecard.json

Verdict, ci_should_fail, per-metric aggregated values, included counts, status counts, authority, baseline state, and run-level diagnostics.

  • Human-readable enough for product conversations.
  • Typed enough for CI and reports.
  • Never claims more than authority allows.
Complete record

runrecord.json

Run id, embedded Scorecard, every per-example Score, provenance fingerprints, and baseline comparability state.

  • Reproducible audit trail.
  • Per-call grouping via explicit example_id/unit_id.
  • Malformed fields fail closed on parse.

Adoption lifecycle

How a check moves from setup to enforcement.

The existing architecture made this sequence explicit, and it is useful enough to preserve in the product map because it is where users experience the boundary between useful evidence and real gates.

Step What happens Authority posture
Install / setup / vendor Plugin or direct CLI vendors the managed runtime, writes manifest/lock, and scaffolds starter host assets. Scaffolds are proposed, informational, and non-authoritative.
Connect Host supplies exported OpenTelemetry, OpenInference, or local JSON traces; live pulls remain planned. Evidence is imported locally and normalized at the edge.
Run first The vendored runtime produces Scorecard, RunRecord, and report. First result is informational by design: no approved threshold, no validated starter gold, no calibrated judge.

End-to-end behavior

How EvalGlass should function as a coherent product.

This is the full operating story stitched from the current docs and site. It is the product behavior future implementation alignment should preserve.

Integration-time

Install without authority.

  • User installs the Claude Code plugin or uses the direct CLI.
  • Skill discovers candidate call sites read-only and produces a non-authoritative plan.
  • Installer vendors managed core/harness/adapters into evals/_evalglass/.
  • Starter host files are scaffolded as proposed, informational, uncalibrated, and empty-authority.
  • The first run is informational by design.
Run-time

Measure without overclaiming.

  • Harness loads evalglass.yaml into typed, authority-safe config.
  • Ports read datasets, exported traces, replay outputs, judge evidence, and result destinations.
  • Runner converges inputs to Examples and EvidenceBundle, checking data policy before effects.
  • Core evaluates, aggregates, fingerprints, resolves authority, compares baseline state, and decides once.
  • Harness persists Scorecard/RunRecord/report and maps verdict to exit code.
Review-time

Improve with evidence.

  • User reads values, status counts, diagnostics, unknowns, and authority reasons.
  • Agent can explain results using typed authority and diagnostics only.
  • User adds examples, validates datasets, calibrates judges, revises metrics, or fixes the app.
  • Baseline comparisons are claimed only when provenance says comparable.
Enforcement-time

Gate deliberately.

  • A metric gates only after host-owned preconditions are met.
  • Required preconditions: validated dataset, approved threshold, metric set to gating, and calibrated judge when relevant.
  • CI acts on the typed verdict/exit code.
  • There is no gate, approve, or certify command.

Non-goals and guardrails

The architecture is defined as much by what it refuses.

These refusals are not marketing caveats; they are product boundaries that keep the scorecard useful.

EvalGlass should do
  • Run locally and in CI from vendored source.
  • Keep project truth and authority in the host repo.
  • Separate value, validity, authority, and verdict.
  • Report missing measurement as missing, not as zero.
  • Require explicit host approval before a gate can enforce CI.
  • Mark future-facing capabilities as next, planned, or experimental.
EvalGlass should not do
  • Behave like a hosted platform or telemetry product.
  • Ask for provider keys on the required path.
  • Let the plugin, agent, report, sink, benchmark, or generated data grant authority.
  • Recompute verdicts outside the Verdict Engine.
  • Auto-tune prompts, edit models, certify safety, or claim broad correctness.
  • Show unshipped capabilities executing as if they were available now.
